# Community apps in the LaraKube Cloud app store (ON HOLD)

## Context
A user who built a Laravel app with LaraKube should be able to publish it to the store, and other users install it on their own servers. Open source first; paid apps come later. The goal: the publisher's repo is the source of truth, the publisher's CI pays for builds, and Cloud stores and serves nothing but verified metadata and its signature.

## Decisions
- **Open source only in v1.** The repo must be public with an OSI-approved license, read from the GitHub API.
- **The publisher's CI builds the image.** It pushes to a public registry (GHCR or Docker Hub) and attaches GitHub build provenance (`actions/attest-build-provenance`). Cloud never builds images.
- **The repo is the source of truth.** Cloud reads everything through the GitHub API at the release tag's commit:
  - **`.larakube.json`:** the marker that it's a LaraKube project, plus the blueprint;
  - **`environments.publish`:** what the app needs;
  - **`larakube-app.json`:** the listing;
  - **`.env.example`:** the buyer's inputs. Its keys minus the ones LaraKube manages, using the same split as the `.env.<env>` seed.
- **Images:** listing images live in the repo (`.larakube/store/…`) and are shown from raw URLs at the commit SHA. Cloud stores nothing.
- **Manifests are regenerated by the LaraKube CLI in the runner,** never taken from the repo's `.infrastructure/`. Cloud signs only manifests LaraKube produced.
- **Cloud stays the only signer.** Once a release is reviewed, it signs the manifest, which pins the image digest. Publishers hold no keys.
- **Requirements vs placement:**
  - **The publisher declares engines:** Postgres, Redis/Valkey, S3, with an optional minimum version.
  - **The buyer picks placement for each service at install:** Own pod, Plex Commons (only if the engine and version match), or External. External keys go into "Needs a value".
  - The publisher's own placement choices are only suggested defaults.
- **Names:** community apps are `publisher/app`; official apps keep their plain slugs.
- **People:**
  - **A publisher is a team** (`publishers.team_id`). A new `TeamPermission::ManageApps`, given to Owner and Admin by default, controls publishing, listing edits and submitting releases.
  - **Maintainers** are chosen by an Admin from team members only, and each must **accept** before they're shown. A pending invite shows nothing, and a maintainer can withdraw at any time.
  - **Contributors** come read-only from GitHub's contributors API for the repo, linking to GitHub profiles. They're cached, not editable, and need no Cloud account.
  - **`larakube-app.json` holds no people.** Names shown on a listing come only from accepted team members or git history, so nobody can list someone as an author without their consent.
- **Commands:**
  - **`larakube app:publish`:** the setup wizard, with a matching Desktop form. Re-runnable. It writes:
    - `larakube-app.json`;
    - the server-less `publish` environment;
    - the CI publish job: build, attest, notify Cloud.
  - **`larakube app:release <version>`:** tags and pushes. Pushing a tag by hand works too.

## Work, in order
1. **Cloud schema** (`database/migrations`; it extends `…create_app_catalog_tables.php`):
   - `release_inputs` (key, label, secret, required, default, help), per release;
   - `release_requirements.min_version`;
   - `app_releases.submitted_by_user_id`, `source_commit`, `attestation_verified_at`;
   - review statuses (`submitted`, `in_review`, `rejected` + `review_notes`);
   - `apps.listed_at`;
   - `apps.repository_url`;
   - `publisher_id` + slug uniqueness, with official slugs reserved;
   - `app_maintainers` (app_id, user_id, invited_by_user_id, accepted_at, position), shown only when `accepted_at` is set;
   - the `ManageApps` permission added to `TeamRole::permissions()` for Owner and Admin.
2. **LaraKube CLI** (it reuses `GathersEnvironmentData`, `seedEnvironmentEnvFile`'s app-key split, and the CI workflow generator in `ConfiguresCloudEnvironment::configureCi`):
   - **A server-less environment mode,** so `publish` has no server and no hosts. It follows the existing `--offline` precedent.
   - **`app:publish`** and **`app:release`.**
   - **`app:render`** (runner-allowed): regenerates the manifests from `environments.publish` and prints a signed-release manifest as JSON. It covers files, images by digest, requirements and inputs.
3. **Cloud submission pipeline:**
   1. The publish API is called by the publisher's CI with an OIDC token that ties the call to the repo.
   2. A runner job reads the repo at the tag, checks `.larakube.json`, verifies the attestation, Trivy-scans the digest and runs `app:render`.
   3. A Filament review queue approves or rejects the release.
   4. Cloud signs on approval.
4. **A generic catalog-driven installer in the LaraKube CLI:** `cloud:apps:install <publisher/app>` reads the signed release instead of the PHP enums. This retires `CloudAppsInstallCommand::APPS` and `config('templates.downloadable')`, so official apps move onto it too.
5. **Store UI** in Cloud and Desktop: the listing, requirements, and per-service placement choice at install.

## Verification
- Run `app:publish` on a sample open-source Laravel app.
- Tag it with `app:release 0.1.0`. Its CI pushes and attests, and Cloud receives the submission.
- Approve it in Filament, and confirm the release is signed and the digest pinned.
- Install it on a NEW server from a runner with no bundled templates, choosing External Postgres. The installer asks for the `DB_*` and app inputs, and the app runs.
- A forged attestation, a wrong repo, or an image changed after approval is rejected.
- Revoking the release makes the CLI refuse it.
- An Admin adds a team member as maintainer. The listing doesn't show them until they accept, and stops showing them once they withdraw. A Member without `ManageApps` can't submit a release.
